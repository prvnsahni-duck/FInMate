# Encryption & Key Management Audit — 2026-07-16

## Summary

FinMate's zero-knowledge implementation is **substantially faithful to its documented architecture**. The core guarantees hold in enforcing code: personal data is encrypted with a PBKDF2-derived AES-256-GCM master key; group data uses a per-group AES-256-GCM key wrapped per-member; the backend never decrypts user content (its server-side `EncryptionService` touches only 2FA secrets and avatar URLs); `group_key_versions` is a true immutable, DB-enforced state machine (partial unique index = one ACTIVE per group); rotation supersedes-then-inserts without overwriting history; wrapped keys are unique per `(version, user)`; and decryption failures are classified, placeholdered, and retried with ciphertext preserved.

Two documented gaps are confirmed as still-open: (6) the backend `GET /groups/:id/keys/me` **ignores the `?versionId=` query param** the client sends and always serves the ACTIVE version, so a member who logs out (or joins post-rotation) cannot re-fetch a SUPERSEDED wrapped key to decrypt pre-rotation history; and (KI-1) group History renders ciphertext titles under a rotated key. A handful of smaller drifts are noted (server-side avatar encryption undocumented; hardcoded fallback `ENCRYPTION_KEY`; `wrappingMethod` metadata dropped on the `/keys` provisioning path; personal scope uses the master key directly rather than a separately-derived UDK).

Nothing here is a zero-knowledge violation — I found no path where the backend can read user content or key material in plaintext.

## Detailed Findings for ⚠ / ❌

### #6 — `versionId` accepted by client, ignored by backend (Medium)
`GroupKeyService.fetchAndCacheGroupKey` builds `.../keys/me?versionId=${groupKeyVersionId}` (`group-key.service.ts:493-495`), and expenses carry a concrete `groupKeyVersionId` (`expense-decryption.service.ts:165-169`, stamped server-side at `expenses.service.ts:649`). But `GroupsController.getMyGroupKey` (`groups.controller.ts:342-352`) takes no query param, and `GroupsService.getMyGroupKey` (`groups.service.ts:1261`) queries `status:'ACTIVE'` unconditionally. Consequence: after a rotation, an expense stamped with a SUPERSEDED version requests that version's key; the backend returns the ACTIVE wrapped key instead; the client unwraps the wrong key and AES-GCM tag verification fails → `keyUnavailable` placeholder (`decryption-state.ts:220-223`). Members who were active before rotation are shielded only because the SUPERSEDED key persists in their IndexedDB vault under `group:${groupId}:${oldVersionId}` — until logout clears it (`clearPersistentCache` → `zkVault.clearAll`). New members can never obtain it. This is the exact gap ARCHITECTURE.md §2.7 admits and KI-1's rotation caveat. Rotation also does not re-encrypt existing ciphertext, so this gap is load-bearing for any real rotation.

### #11 — Server-side encryption scope broader than documented + weak default (Medium)
ARCHITECTURE §8 and PROJECT_DECISIONS describe `ENCRYPTION_KEY` as protecting 2FA secrets. Implementation also encrypts `profile.avatarUrl` with the same server key (`users.service.ts:115,130`) — a non-ZK server-held field not documented as encrypted. Separately, `EncryptionService` falls back to a hardcoded literal secret when the env var is unset (`encryption.service.ts:18-19`); if this ever runs in production without `ENCRYPTION_KEY`, all 2FA secrets are encrypted under a public constant. Recommend removing the fallback (fail-fast at boot) and documenting the avatar field.

## Undocumented Behavior Found

- **`wrappingMethod`/`wrappingAlgorithm` dropped on `/keys` provisioning.** `provisionGroupKeys` and `rotateGroupKey` persist rows without setting `wrappingAlgorithm` (`groups.service.ts:1245-1252, 1378-1385`), even though `WrappedKeyEntryDto` accepts `wrappingMethod` (`group-key.dto.ts:41-46`). Only the direct-invite path sets it (`groups.service.ts:582`). The client compensates by sniffing the wrapped-key format (`wrappedKey.includes(':')` → symmetric vs asymmetric, `group-key.service.ts:518-525`). Functional but fragile; the stored algorithm metadata is unreliable.
- **Personal scope uses the master key directly.** There is no separate "UDK derived from Master Key" as the key taxonomy (`zk_group_key_provisioning_architecture.md` §1) describes; `resolveKey` returns `loadKeyFromSession(email)` (the PBKDF2 master key) for personal expenses (`expense-decryption.service.ts:199-202`). No security impact, but the two-tier Master→UDK derivation is documentation-only.
- **Audit metadata stores ciphertext titles without a version stamp** (`expenses.service.ts:726,1093`), surfaced verbatim in History (`groups.service.ts:936-945`). Not a plaintext leak (consistent with ZK) but the documented KI-1 rotation caveat: no `groupKeyVersionId` in audit metadata means client-side history decryption uses the ACTIVE key only.
- **Group key generated as extractable and cached as such by the minter.** `generateDataKey` creates `extractable:true` (`encryption.service.ts:377`, required for wrapping) and `createGroupKey` caches that extractable handle in memory + vault (`group-key.service.ts:230-237`), whereas keys fetched/unwrapped from the backend are non-extractable (`unwrapKey` default `extractable=false`, `:520-524`). The threat-model claim that vault keys are always non-extractable (`zk_group_key_provisioning_architecture.md` §4) is thus not universally true for the key originator's session. Low risk.
- **No server-side proof the provisioner holds the real group key.** `provisionGroupKeys`/`rotate` trust whatever wrapped blob the client uploads (`groups.service.ts:1244-1252`). This is inherent to the zero-knowledge model (the server cannot verify) and is acceptable, but worth recording: a malicious active member could upload a garbage wrapped key for another member, causing a decryption DoS (not a confidentiality break). Matches the documented "Backend Compromise" medium-risk row.

## Positive Confirmations (enforcing code seen)

- One-ACTIVE-version-per-group is enforced at the database level via partial unique index (`1719000000000-AddGroupKeyVersioningModel.ts:27-31`), satisfying the SECURITY_VERIFICATION_CHECKLIST "One ACTIVE version per group is enforced in DB."
- Rotation cannot overwrite historical wrapped keys: `provisionGroupKeys` guards with `if (!existing)` (`groups.service.ts:1244`) and rotation inserts under a *new* version id; `@Unique(['groupKeyVersion','user'])` prevents dupes within a version.
- Logout clears both tiers: master key (`encryptionService.clearKey`) and the entire vault (`groupKeyService.clearPersistentCache` → `zkVault.clearAll`) at `auth.state.ts:146-148`, plus IndexedDB fallback map cleared (`zk-key-vault.service.ts:214-215`).
- TIK is never transmitted: invite DTOs carry only `wrappedGroupKey` + `inviteKeyHash` (`group.dto.ts:127-133`); the raw TIK lives only in the link hash fragment per the flow docs.
