# Expense Module Audit — 2026-07-16

## Summary

The Expense module is, on the whole, **substantially compliant** with the documented zero-knowledge and ledger guarantees. Client-side encryption of titles/notes is enforced end-to-end (frontend encrypts before POST; backend DTOs reject non-ciphertext via `@IsCiphertext`; the backend never decrypts), amounts are stored plaintext, the single-record/aggregation model holds, group-key-version references are wired into `expenses`, settlement/currency-consistency rules are enforced transactionally, and household ledger finalization runs inside a transaction. However, several documented guarantees are **only partially met**: the "7-day restore grace period" is actually implemented as *calendar-month-of-deletion + 7 days*; `expense_splits` are **not** soft-deleted and carry **no version column** despite ARCHITECTURE §4.2–4.3 implying "expenses and splits" do both; recurring-expense templates encrypt group data but carry **no `groupKeyVersionId`**; and editing an expense **silently deletes settled splits** and resets `isSettled=false` with no adjustment trail. Recurring group expenses also skip the currency-match validation applied to one-off expenses. None of the findings expose plaintext titles to the server, but the split/version/restore drifts and the settled-split reset are real correctness/consistency gaps worth scheduling.

## Detailed findings

### #4 — Recurring templates + post-rotation update lack key-version integrity (⚠ Partial)
`Expense` correctly carries `groupKeyVersion` (`expense.entity.ts:52-53`) and it is stamped on create (`expenses.service.ts:632-649`), by the scheduler (`recurring-expenses.scheduler.ts:117-148`), and backfilled in migration `1719000…:83-105,182-190`. Two gaps:
1. `RecurringExpense` encrypts `title`/`description` with the group key (`recurring-expenses.service.ts:263-265` via FE) but has **no `groupKeyVersionId`** column (`recurring-expense.entity.ts:20-23`; `DATABASE_SCHEMA.md:252-270` omits it). PROJECT_DECISIONS ("reference the key version used where applicable") applies to this group-scoped encrypted resource.
2. In `updateExpense`, the key version is only set when missing: `if (expense.group && !expense.groupKeyVersion)` (`expenses.service.ts:987-992`). After a key rotation, the FE re-encrypts the title with the **active** key (`group-key.service.getGroupDataKey`), but the persisted `groupKeyVersion` still points to the **old** version — a stored ciphertext/version mismatch that can cause a wrong-version decrypt.

### #5 — Restore window and split soft-delete diverge from docs (⚠ Partial)
ARCHITECTURE §4.3 states "restorations within a 7-day grace period." The code computes `graceEnd = last day of deletion month + 7 days of the following month` (`expenses.service.ts:1189-1203`) — e.g. an expense deleted on the 1st is restorable for ~37 days, and one deleted on the 28th for ~10 days. Behavior is inconsistent with the documented flat 7 days.
ARCHITECTURE §4.3 also says "Expenses **and splits** use soft-deletion patterns through `@DeleteDateColumn()`." `ExpenseSplit` has **no** `@DeleteDateColumn` (`expense-split.entity.ts`) and `DATABASE_SCHEMA.md:212-224` confirms no `deleted_at`; on update splits are physically deleted (`expenses.service.ts:1008-1010`). Ledger split history is therefore not preserved on edit.

### #6 — Splits not individually version-locked (⚠ Partial)
ARCHITECTURE §4.2 ("entities contain a `@VersionColumn()`") is not met for `ExpenseSplit` (no version column, `expense-split.entity.ts`; `DATABASE_SCHEMA.md:212-224`). Concurrency for splits relies entirely on the parent `Expense.version` gate at `expenses.service.ts:879-885`. Additionally `deleteExpense` and `restoreExpense` accept no version and perform no `CON_VERSION_CONFLICT` check (`expenses.service.ts:1107-1146,1154-1216`), so a stale-client delete/restore can race an edit.

### #10 — Editing an expense silently discards settled splits (⚠ Partial, High)
`updateExpense` unconditionally runs `ExpenseSplit.delete({ expense })` then `persistSplits(...)` which recreates every split with `isSettled: false` (`expenses.service.ts:1008-1021`; `persistSplits` `470-478,513-521`). There is no check for `isSettled=true` splits and no adjustment/audit of the settlement reversal. A split previously marked settled (`expense-split.entity.ts:44-48`) is silently un-settled and its `settledAt` lost. This is the "silent history mutation" the checklist warns against; only the household previous-month lock (`expenses.service.ts:226-235`) prevents it, and only for household groups.

### #11 — Recurring group expenses bypass currency-consistency validation (⚠ Partial)
One-off group expenses enforce `dto.currency == group.currency` with `EXP_CURRENCY_MISMATCH` (`expenses.service.ts:586-594`). `createRecurringExpense`/`updateRecurringExpense` perform no such check (`recurring-expenses.service.ts:219-291,347-422`), and the scheduler copies `template.currency` verbatim into generated expenses (`recurring-expenses.scheduler.ts:140`) without re-validating. A recurring template created in a non-base currency will repeatedly emit expenses that violate the group's currency-consistency invariant (ARCHITECTURE §5).

## Undocumented behavior found

1. **`direct_shared` encryption scope is defined but forbidden.** The entity, DTOs, migrations, and `EncryptedExpenseKey` plumbing all support `direct_shared` (`expense.entity.ts:79-82`, `create-expense.dto.ts:93-101`, `getWrappedContentKeys`/`wrappedContentKeys` in `expenses.service.ts:264-289,662-675`), but `validateExpenseEncryptionMetadata` unconditionally **rejects** it (`expenses.service.ts:340-352`) and the frontend never emits it (`expenses.service.ts:50-72` only produces `personal`/`group`). Dead, undocumented feature surface.
2. **Restore grace period** is calendar-month-of-deletion + 7 days, not a flat 7 days (see #5) — no doc describes this rule.
3. **Post-rotation update key-version staleness** (see #4.2) — undocumented and potentially decrypt-breaking.
4. **Settled-split silent reset on edit** (see #10) — no doc mentions that editing clears settlement state.
5. **Settlement `note`** is labeled "Client-Side Encrypted" (`DATABASE_SCHEMA.md:242`) but the backend accepts and stores it without `@IsCiphertext` enforcement (`settlement.dto.ts:31-33`, `settlements.service.ts:380-381`), unlike expense titles — a client could persist a plaintext note.
6. **Frontend fallback to plaintext.** `encryptPayload` returns the raw payload unencrypted when no session email is present (`frontend/.../expenses.service.ts:39-92`, `return payload`). Backend `@IsCiphertext` would reject it, so no plaintext reaches storage, but the client-side branch is an undocumented failure mode.
7. **Audit metadata carries the ciphertext title** on create/update/delete/restore (`expenses.service.ts:725-729,1091-1095,1139-1143,1234`) — documented as KI-1 but reconfirmed here; it does not carry `groupKeyVersionId`, matching the KI-1 rotation caveat.
8. **`ledgerMonth` derives from `expenseDate.slice(0,7)` on create** (`expenses.service.ts:651-654`) but analytics carry-forward keys off `ledgerMonth` OR `expenseDate` (`expenses.service.ts:1888`) — mixed keying that is not documented.
