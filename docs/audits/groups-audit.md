# Groups Module Audit — 2026-07-16

## Summary

The Groups module (backend `backend/src/app/groups/`, entities in `shared/data-models/src/lib/`, frontend `frontend/src/app/features/groups/`) is largely well-implemented against the documented guarantees. Core zero-knowledge invariants hold: **one Group Key per group with versioning** (no duplicate keys on invite), **currency lock after activity**, **archive-instead-of-delete**, **owner-cannot-leave**, and **per-ledger-month contributions** all have real enforcing code.

However, the audit surfaced several gaps:

- **❌ Privilege escalation (undocumented, high severity):** `updateMember` lets _any_ active member (including `viewer`/`member`) change _any_ member's role to `owner`, silently demoting the real owner. No caller-role check guards role changes.
- **📋 `trip` group type is roadmap-only** — documented in `ARCHITECTURE.md` but not implemented (DTO, entity, DB CHECK, and DATABASE_SCHEMA.md all only allow `normal`/`household`).
- **⚠ Audit coverage gaps:** key rotation, key provisioning, invite-link creation, invite-token regeneration, and contribution changes write **no** audit log.
- **⚠ History decrypt caveat (KI-1) is current behavior:** decrypt happens client-side in `GroupsService.getHistoryLogs` against the **active** key only; post-rotation entries show the placeholder. Backend still stores raw ciphertext with no `groupKeyVersionId`.
- **⚠ "Leaver retains historical access" is not what the code does:** leaving fully revokes API access (all queries filter `joinStatus='active'`), and the member's wrapped key is never revoked/rotated (cryptographic access is not cut).
- **⚠ `spectator` role only partially enforced** — honored in the expenses split logic, but absent from the `GroupRoles` decorator type and every `@GroupRoles(...)` list, so a spectator is denied member-list/management routes.
- **⚠ Permanent, non-expiring `group.inviteToken`** join link with no revocation beyond regeneration.

## Detailed findings for each ⚠/❌

### ❌ 11-A (High) — Privilege escalation: any member can seize ownership

`MembersController.update` is gated by `@GroupRoles('owner','admin','member','viewer')` (`members.controller.ts:60`), so `member` and `viewer` pass the guard. Inside `GroupsService.updateMember`, the role-change branch has **no caller-role check** — the comment even states the intent: "Role can be changed by any member, to any role, at any time" (`groups.service.ts:700-741`). When `dto.role === 'owner'`, it demotes the current owner to `admin` and promotes the target (`:702-718`). Net effect: a low-privilege member (or viewer) can promote themselves to `owner`, demote the real owner, and then take any owner action. This also renders the owner-cannot-leave protection (#2) bypassable via self-transfer. Contrast with the correctly-guarded `removeMember`, which _does_ check caller role (`:861-873`). Recommend requiring caller `owner` (or `owner`/`admin` per policy) for any role change, and specifically restricting promotion-to-owner to the current owner.

### ⚠ 1 — spectator role not enforceable on member routes

`GroupRoles(...)` type is `('owner'|'admin'|'member'|'viewer')` only (`group-roles.decorator.ts:3-5`) and no route lists `spectator`. `GroupRolesGuard` denies when `!roles.includes(membership.role)` (`group-roles.guard.ts:74-79`). A spectator is honored in expense split/settlement exclusion (`expenses.service.ts:506,567`) but would be **forbidden** from `GET/PATCH/DELETE /groups/:id/members`. Inconsistent enforcement of a documented role (`DATABASE_SCHEMA.md:162`, `ARCHITECTURE.md:268`).

### ⚠ 4 — invite lifecycle: no revoke + permanent link

`group_invites` rows expire after 7 days and flip to `expired` on access (`groups.service.ts:590-591,984-987,1071-1075`), but there is no endpoint to revoke a still-pending invite. Separately, `group.inviteToken` (`group.entity.ts:49-50`) is a permanent, never-expiring join link; `regenerateInviteToken` (`:950-974`) rotates it but performs no audit log and is the only mitigation. Anyone holding an old link keeps working access until regeneration.

### ⚠ 5 — leaver access semantics mismatch

The guarantee (`ARCHITECTURE.md:81`) says leavers "retain access only to historical data they were authorized to see." The code instead **fully revokes** API access (every group read filters `joinStatus='active'`), while **not** revoking or rotating the member's wrapped Group Key on leave (`removeMember:833-856`; no delete of `MemberWrappedGroupKey`). So the leaver loses server reads entirely yet keeps the raw key material to decrypt any previously-synced/cached ciphertext. Either the doc or the implementation should be reconciled (and key rotation on membership change considered).

### ⚠ 6 — trip type roadmap-only

`ARCHITECTURE.md:267` lists trip as a group type, but it is absent from `group.entity.ts:36-37`, `dto/group.dto.ts:54-58`, migration `1718200000000`, and `DATABASE_SCHEMA.md:147`. Submitting `groupType:'trip'` fails DTO validation. Mark as roadmap / doc drift.

### ⚠ 9 — history decrypt is the KI-1 interim, not the agreed end-state

Confirmed current behavior matches KNOWN_ISSUES.md KI-1's "shipped interim (Option 3)": client decrypts `title`/`newTitle`/`previousTitle` with the **active** group key only (`frontend/…/groups.service.ts:91-131`). After a key rotation, older audit entries decrypt-fail and render `DECRYPTION_FAILED_PLACEHOLDER` because audit metadata carries no `groupKeyVersionId` (backend stores raw ciphertext, `groups.service.ts:943`). The agreed v2.1 fix (Option 1 — neutral phrasing, stop storing titles) is not implemented.

### ⚠ 10 — audit gaps on config/security actions

Five state-changing group operations emit no `AuditLog`: `rotateGroupKey`, `provisionGroupKeys`, `createGroupInvite`, `regenerateInviteToken`, `updateContributions` (confirmed: no `writeAuditLog` call after `groups.service.ts:1138`). Key rotation in particular is a security-relevant event (§6 audit logging) and should be recorded with actor + ipHash.

## Undocumented behavior found

1. **Role change is unauthenticated by role (see 11-A)** — the single most important undocumented gap; enables ownership takeover.
2. **Auto-provisioning of shadow users on invite** — inviting an unknown email/phone silently creates a `User` with `status:'invited'` and an argon2-hashed random password; phone-only invitees get a synthetic `<phone>@placeholder.finmate` email (`groups.service.ts:185-211,485-514`). Placeholder emails are stripped from invite/member responses (`:1008,1044,1425`). Not described in the group docs.
3. **Two parallel invite mechanisms** — durable `group_invites` (with wrapped key + expiry) _and_ a perpetual `group.inviteToken` fallback used by `getInviteDetails`/`joinGroupByToken` (`:1018-1052,1083-1092`). The fallback path grants membership with role `member` and provisions **no** wrapped key.
4. **`updateMember` accepts self-accept of invitations** (`joinStatus:'active'`, `:747-752`) — an invited user's own PATCH is allowed through the guard's self-update exception (`group-roles.guard.ts:62-72`); this dual accept path (also `joinGroupByToken`) is undocumented.
5. **Re-invite reuses a `left`/`removed` member row** and resets role/timestamps (`:531-546`) rather than creating a new membership; combined with no key rotation on leave, a re-invited user may still hold the old key.
6. **`writeAuditLog` swallows all errors** (`:138-140`) by design ("never block primary op") — acceptable but means audit loss is silent/unobservable.

Priorities: address **11-A (High)** first; then audit-coverage and invite-revocation (Medium); KI-1 end-state and trip-type doc reconciliation are Low.
